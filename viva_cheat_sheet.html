Computer Networks Course Project — Viva Evaluation Guide

Structured 11-step walkthrough with commands and technical explanations.

Step 1 Display: Soumen
Topology and Machine Inventory Presentation
open ~/Desktop/cn-project/topology.html
Explanation to Faculty: "Here is our complete four-node distributed topology. Machine 1 acts as our Primary Authoritative DNS Resolver. Machine 2 serves as the Edge Reverse Proxy and Load Balancer terminating TLS on port 443. Machine 3 and Machine 4 run two independent backend instances on ports 5002 and 5001 respectively. Additionally, Machine 3 hosts our Backup DNS Resolver, and Machine 4 acts as a Standby Edge Node."
Step 2 Action: Any Machine
LAN Reachability Verification
ping -c 2 10.7.3.54; ping -c 2 10.7.2.62; ping -c 2 10.7.26.82
Explanation to Faculty: "All four machines are connected to the same private subnet. We have verified basic Network Layer reachability across all nodes using ICMP echo requests with zero percent packet loss."
Step 3 Action: Client Machine
Private Domain Resolution
dig app.team1.test +short
Explanation to Faculty: "The client queries our private DNS server over UDP port 53. The domain app.team1.test successfully resolves to the Edge IP 10.7.2.62 with an authoritative TTL of 30 seconds."
Step 4 Action: Client Machine
Secure HTTPS Delivery Without Insecure Flags
curl -i https://app.team1.test/nginx-health
Explanation to Faculty: "The client establishes a secure HTTPS session over HTTP/2. Because our team Local Root CA is installed and trusted within the macOS system keychain, certificate validation succeeds natively without requiring the insecure -k flag."
Step 5 Action: Client Machine
Round-Robin Load Balancing Across Backends
for i in 1 2 3 4; do curl -si https://app.team1.test/api/status | grep "x-backend:"; done
Explanation to Faculty: "Successive requests show alternating response headers between X-Backend A and X-Backend B. Nginx is actively distributing traffic across both upstream instances using round-robin scheduling."
Step 6 Display: Wireshark
Protocol Stack Packet Evidence
Explanation to Faculty: "In this capture, we observe the complete protocol stack in chronological order: first, a UDP query on port 53 for name resolution; second, a TCP three-way handshake (SYN, SYN-ACK, ACK) on port 443; and third, the TLS 1.3 handshake exchanging ClientHello, ServerHello, and encrypted application data."
Step 7 Action: Client Machine
HTTP Caching and Conditional Validation
curl -si https://app.team1.test/api/cache-demo
Explanation to Faculty: "The endpoint returns Cache-Control max-age 60 along with an ETag header. When the client sends a conditional request with If-None-Match, the server validates the entity tag and responds with 304 Not Modified, conserving network bandwidth."
Step 8 Action: Rishav & Client
High-Availability Backend Failover
for i in 1 2 3 4; do curl -si https://app.team1.test/api/status | grep "x-backend:"; done
Explanation to Faculty: "After terminating Backend A, Nginx detects the upstream failure via passive health checking parameters (max_fails=2 and fail_timeout=10s) and automatically redirects 100 percent of client requests to healthy Backend B without user-facing downtime."
Step 9 Action: Client Machine
Service Isolation via macOS Packet Filter
curl -v --connect-timeout 3 http://10.7.24.85:5002/api/status
Explanation to Faculty: "Using macOS packet filter (pf) rules, direct ingress traffic to port 5002 is strictly blocked for general clients and dropped silently, ensuring that backend services can only be accessed internally through the reverse proxy edge."
Step 10 Action: Team Diagnosis
Systematic Layer-by-Layer Troubleshooting
dig app.team1.test +short
nc -zv 10.7.2.62 443
curl -Iv https://app.team1.test
Explanation to Faculty: "We diagnose network faults systematically from bottom to top: first, verifying DNS resolution; second, testing Transport Layer TCP port reachability; third, inspecting the TLS handshake and trust chain; and finally, verifying Application Layer upstream status codes."
